## A1. 第 4 关的机器人胜率只有 25%，是五关里唯一的断崖

**现象**：五关胜率 75% / 47% / 49% / **25%** / 52%。第 4 关比第 3 关低 24 个点，比第 5 关低 27 个点。

**证据（三轮，全部可重跑）**

1. 九次改地图，九次更差 —— 降追兵 19.8%、黑灯加到 12 秒 14.6%、主廊加断线柱 **0%**、
   窄段下加逃生井 25.0%、开补给 17.7%、体力 +20% 17.7%、修 3 块掩体 20.8%、
   去掉一个窄段 24.0%、机器人逃跑改躲掩体 **0%**（48 局配对翻盘 0:13，p=0.0002）。
2. 败局切片（`scripts/diag_level4.py`）：**96 局里"一次都没被发现"的局是 0 局**；
   第一次被看见中位 7.3 秒；整局 60%~70% 的时间在逃跑，**赢的局也一样**。
3. 改尺子也没用（`scripts/ab_look.py`，同种子配对 96 局）：把机器人的"前瞻"从 6 格拉到 12 格，
   首次被发现 7.3→10.0 秒（真的做到了），胜率 25.0%→27.1%，**p = 0.86**。

**为什么改不动**：一个算术。满体力冲刺 100/34 = 2.94 秒，玩家冲刺 6.5 对追兵 4.5，
相对速度 2.0 格/秒 → 最多拉开 **5.9 格 < 视野半径 6.5 格**。
"被看见之后跑掉"在这个游戏里数学上不成立；而躲也没用（柱子全是 2×2 贴墙，
追兵沿中线追，绕两格视线就接回来）。

**决定**：不改关卡、不改全局常量（玩家速度、视野半径一动，五关全变）。
这一关的形状就是"三个没有遮挡的窄段 + 一条回程直廊"。

**玩家侧的兜底**：辅助模式（菜单按 A）把追兵速度 ×0.88（4.5→3.96，低于走路 4.4）、
视野 ×0.82、警觉时长 ×0.60，实测同一批 60 个种子：**70% → 98.3%，翻盘 18:1，p = 7.6e-05**，
辅助局不计纪录。也就是说这一关"过得去"是靠 A 键，不是靠难度曲线。

**如果非要改**：动"被看见之后还有什么可做"（例如蹲伏静止=隐蔽），那要新增机制、
要重测五关、要重写难度表。这是 v1.9 的事，不是这一个版本的补丁。

**复查**：`python scripts/diag_level4.py --runs 48`、`python scripts/ab_look.py --level 3 --runs 96`

## A2. 第 4 关三个窄段的两侧没有掩体

**现象**：主廊收窄段（x=26..32 / 49..55 / 62..68）压到 4 格宽，两侧就是墙，
而玩家最需要掩体的地方恰好是这里。

**来历**：掩体表里有 7 块坐标是在收窄段之前画的，坐标跨进了后来被 `SWITCH_NARROW`
填掉的墙行。`add_cover` 的规则是"整块里只要有一格是墙，整块跳过"—— 静默跳过，
不报错、不提示。于是**配置了 26 块，"画出来"只有 19 块**，少掉的几乎全在窄段两侧。
这个状态存在了好几个版本，任何测试都不会红。

**证据**：v1.8.10 把其中 3 块挪到窄段外侧的有效坐标试过 —— 96 局 **20.8%**（基线 25.0%），
更差。原因和 A1 同源：柱子给的是"绕一步躲一下"，而这一关的死法是"警报响了之后跑不掉"。

**决定**：认成设计决定。同时把 7 块死配置**从表里删掉**（不是因为它们有害，
而是因为它们会**复活**：只要有人动一下 `SWITCH_NARROW`，那 7 块就会突然冒出来，
地图跟着变，而没有任何东西提示你）。删前删后五关地形 sha256 完全一致，不是改图。
`test_w35` 现在静态检查"没有一块掩体配置落在收窄段填掉的墙行里"。

**复查**：`python scripts/test_w35.py`

## B1. 二进制只发 Windows

**现象**：GitHub Release 只有一个 `StealthProtocol-vX-win64.exe`。macOS / Linux 用户没有双击即玩的东西。

**能做到什么**：**源码三平台可跑**。字体是唯一的历史障碍 ——
以前写死 `microsoftyahei / msyh / simhei` 三个 Windows 字体名，换系统就是全屏中文方块
（pygame 找不到名字会静默退回默认位图字体，那个字体没有中文字形）。
v1.8.10 换成跨平台候选链（Windows 雅黑/黑体 → macOS 苹方/冬青 → Linux Noto CJK/文泉驿 → Arial Unicode MS），
调用方式不变，Windows 上逐像素一致（`test_w35` 断言中文字形真的画出来了，不是两个一样的方块）。
CI 每次推送都在 **ubuntu-latest** 上装 `fonts-noto-cjk`、跑全套脚本 + 入口自检，
所以"源码能在 Linux 跑"这句话每推一次都被机器验一次，不是一句宣传。

**做不到什么**：macOS 的二进制。没有 mac 机器 —— CI 的 macOS runner 是有的，
但要签名/公证才有意义，不签名的话用户双击会被 Gatekeeper 拦下，实测体验比"自己装 Python"还差。
所以不做，也不假装做。

**决定**：源码支持三平台（CI 验 Ubuntu，macOS 靠 pygame 的通用性 + 字体链覆盖，
但**没有被机器验证过**，这句话写在这里就是为了不让人误以为验证过）；
二进制只发 Windows。

**复查**：`.github/workflows/test-suite.yml` 的 `runs-on: ubuntu-latest` 与 `安装中文字体` 两步

## B2. 难度表的数字不能并排比

**现象**：README 里同时存在"第 4 关 25%"和"第 4 关 70% → 98.3%"，差 45 个点。

**这不是矛盾，是两把尺子**：25% 是 `measure_levels.py` 的难度基线（不带枪、前四关不捡补给、
只看"能不能通关"）；70%/98.3% 是 `measure_assist.py` 的辅助 A/B（带枪、捡补给、同一批种子开/关各跑）。
能并排的只有同一份口径下的两行。

**决定**：不合并、不取舍。两处数字各自注明口径，`test_w31` 对账难度表与脚本、`test_w32` 守辅助模式口径。

**复查**：`python scripts/test_w31.py`、`python scripts/test_w32.py`
