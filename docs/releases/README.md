# 发布说明（Release notes）

这个目录里的 `<tag>.md` 会被 `.github/workflows/release.yml` 直接拿来当 Release 正文。

## 约定

- 文件名必须是 **tag 名**：`v1.9.0.md`、`v1.10.2.md`。打成 `1.9.0.md` 或 `v1.9.0-release.md` 都读不到。
- **第一行必须是 `# 一句话说这一版干嘛`**。这行会被抽出来当 Release 标题，
  最终显示成 `v1.9.0 —— 一句话说这一版干嘛`，正文里不再重复出现。
- 不用写安装说明：脚本会自动在末尾补一段（下载哪个文件、存档落在哪、怎么自检）。
- 没有这个文件也能发 —— 会退化成"上一个 tag 之后的 commit 列表"。
  那种正文能看，但它只回答了"改了哪些行"，没回答"这一版是干嘛的"。

## 本地预览

```bash
python scripts/release_notes.py --tag v1.9.0 --print
```

`--print` 走的是和 CI 完全相同的路径（先找本目录、找不到再退回 git log），
所以看到什么，Release 上就是什么。

## 为什么要有这个目录

`git tag` 只带一个名字和一条 message，而 Release 页面是给**没装环境的人**看的：
他先看标题和第一段，再决定要不要下那 28 MB。那段话只能是人写的。

把正文放进仓库而不是敲在 `gh release create --notes "..."` 里，还有两个附带好处：
它在 PR 里是可以被 review 的，而且**发布之后还能改** —— 发现写错了，改文件、重跑流水线就行，
不用在网页上重新粘一遍。
