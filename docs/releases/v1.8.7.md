# 把发布这件事交给 tag

上一版（v1.8.6）的发布流程是这样走完的：本地打包 → 手动改名 → 手动算哈希 → 手动 curl 建 Release → 手动传 28 MB 附件 → 手动发 tag。

每一步都成功过，所以它看起来是"流程"。但它是**一套只在我这台机器上成立的动作**：路径、代理、GitHub 令牌、中文文件名编码，全都隐式依赖当前这个终端。

这一版把整条链子挪进 CI：**`git push origin v1.8.7` 之后，什么都不用做。**

## 现在的发布长什么样

```
git tag -a v1.8.8 -m "..."     ← 唯一的人工动作
git push origin v1.8.8
         │
         ├─ gate   测试门禁（与 CI 跑同一份清单）
         ├─ build  windows-latest 打包 + --selfcheck + sha256
         └─ publish 建 Release、上传 exe、贴正文
```

三个 job 串行：门禁不过、打包不跑；打包不自检通过、不发布。

## 四处"必须这么写"的地方

**一、测试清单只能有一份。** 发布前要跑的测试，和每次 push 跑的是同一批。如果 `ci.yml` 和 `release.yml` 各抄一遍清单，迟早会漂 —— 加了 `test_w27` 只改了一边，于是"发布前测试全绿"这句话只对 push 成立，对 tag 不成立，而且**它不会报错**。所以抽成了 `test-suite.yml`（`workflow_call`），两个地方都 `uses:` 它。

**二、exe 的文件名不能让流水线去改。** 默认产物叫 `潜行协议.exe`。在 Windows runner 上"重命名一个中文文件、再把结果交给下一个 shell 步骤"，中间横跨 PowerShell / cmd / Git Bash 三套编码（cp936 / cp65001），随时能咬人。与其在流水线里跟编码搏斗，不如让打包器一开始就产出最终名字：`build_exe.py` 加了 `--name`，CI 传 `StealthProtocol-v1.9.0-win64`。**中文名留给双击玩的人，ASCII 名给机器。**

**三、Release 正文要能从仓库里读出来。** 敲在 `gh release create --notes "..."` 里的话，发完就进了网页，改不了、也 review 不了。现在约定 `docs/releases/<tag>.md`，首行 `# 一句话` 会被抽成标题。

**四、`publish` 不能 checkout 被发布的 tag。** 这一条是第三次失败换来的：被打包的东西要来自 tag（前后必须同一个提交），打包和发布用的**工具**要来自最新提交 —— **这两条要求是相反的**。混成一个 ref，结果就是"修了流水线的 bug 却永远用不上"：修 bug 的脚本写在 `main` 上，流水线每次却从老 tag 里取工具，那个脚本在那一版里根本不存在。

## 为什么正文要留一条"自动生成"的退路

手写 notes 是理想路径，但它有个前提：**人记得写**。

自动生成（上一个 tag 之后的 commit 列表）回答不了"这一版是干嘛的"，可它能保证"忘了写也不会发出一版空正文"。所以两条路都在：有 `<tag>.md` 就用手写的，没有就拼 commit 列表。

这也是这一版真正想留下的东西 —— **不是"发布更快了"，是"发布不再依赖我记得什么"。**

## 第一次跑就翻车了（而且翻得很有价值）

打完 tag，流水线跑起来：

```
gate      ✓ 测试全绿
build     打包 ✓ → 自检 ✗ UnicodeEncodeError: 'charmap' codec can't encode
publish   跳过
```

本地这一串是绿的。差别在代码页：**这台机器是中文 Windows（cp936），中文写得出去；GitHub 的 runner 是英文 Windows（cp1252），中文写不出去。** 自检第一行就是中文，`print` 直接抛异常，退出码变 1 —— "自检不通过"其实是"日志写不出去"。

更难看的是，这个坑第 23 章就记过（emoji 撞 cp936 的 cmd），当时的修法是把 `✅` 换成 `[OK]`，**只改了台词没改机制**，所以它换了个方向回来。

这次改的是机制：`_harden_console()` 在 `main()` 最前面重配 stdout/stderr —— 接管道/重定向时用 UTF-8（内容不丢），在终端里保留系统编码、只放宽 `errors`。`test_w28` 钉住四条，其中一条验证过"摘掉修复必须变红"，报错和 CI 上逐字相同。

**这条流水线的第一个产出不是 exe，是一个"只在我机器上成立"的漏洞被机器暴露出来。** 不只是流程只在本机成立，验证也差点只在本机成立。

## 后面又翻了两次，两次都不像 bug

**第二次：`HTTP 500`。** 建 draft、传附件都成功，最后一步"把 draft 转成已发布"被 GitHub 回了一个 500。手动对同一个 release 发 PATCH 却是 3 秒成功——那就逐字段试：`{name}` 500、`{body}` 500、`{name,body,draft}` 500、**`{name,body,draft,tag_name}` 成功**。

必须带 `tag_name`。诱因是我中途删过又重建 v1.8.7 的 tag，release 内部那条 ref 关系脏了，服务端更新时要重新按 tag 解析才定位得到。而 `gh release edit` 用 release id 定位、payload 里没有 `tag_name`，于是每次都挂，报错只有一行 `HTTP 500`，没有 payload 可查。

改用 `scripts/publish_release.py` 自己发请求，显式带 `tag_name`。**封装替你做的那个决定，出事时最难查**——它省掉的那一行为什么不能省，正是这次要回答的问题。

**第三次：找不到脚本。** `python: can't open file 'scripts/publish_release.py': No such file or directory`。

`publish` job 里 checkout 的是 tag `v1.8.7`，而那个提交里没有这个脚本——它是修流水线时才写的。这不是路径笔误，是职责划分错了：

- `gate` / `build` 必须 checkout **tag**（被打包的是那个提交，前后得是同一个）
- `publish` 必须 checkout **触发 ref**（打包和发布用的工具，要最新的）

混成一个 ref 的后果是"**修了流水线的 bug 却永远用不上**"：修 bug 的脚本写在 main 上，流水线每次却从老 tag 里取工具。**工具和被加工物必须解耦。**

## 验收

- **26 个测试全绿**，新增 `test_w28`（4 条）：cp1252 的流加固后写得进中文 / `--selfcheck` 在 `PYTHONIOENCODING=cp1252` 下退出码 0 / 输出里仍有中文（不是靠丢内容换来的绿）/ 参数错误的中文提示也活得下来
- `release_notes.py` 两条路径都验过：手写命中（读 `docs/releases/<tag>.md`，抽首行当标题）、自动生成（`git log` 区间 + 安装说明）
- `build_exe.py --name` 不影响默认行为：不带参数时仍是 `dist/潜行协议.exe`
- 门禁 job 与 `ci.yml` 是同一份 workflow，不存在"发布跑的和开发跑的不一样"
- **幂等真的跑过**：同一 tag 重发走"已存在 → 更新"，`[OK] 更新 Release draft=False`，附件 `--clobber` 覆盖，不报 409；重发会重新打包，所以正文里的 sha256 每次由 build 产出、不手抄
- **建的分支也跑过**：删掉 Release（保留 tag）后重发，走 404 → 新建，附件、正文、`draft=false` 一次到位
